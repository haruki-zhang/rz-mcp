# RZ/G3L MCP Server：探索阶段工作计划

> 依据：`EPAE_MCP_Feasibility_Study.pptx`（2026/10/30，Team Sharing · Early Exploration Phase）
> 状态：草案 v0.1
> 适用范围：RZ/G3L 试点。后续扩展到其他 device 时作为模板参考

---

## 1. 结论先行

可行性报告已经得出 **"可行"** 的结论，并把下一步定为：

> **RZ/G3L prototype: HW UM → register lookup + section search**

所以现阶段的关键问题已经不是"MCP 能不能做"，因为 MCP 协议和 SDK 都很成熟，写一个 server 只要几天。真正决定成败的有下面三点：

1. **数据能不能做准**：能不能从 RZ/G3L 的 HW UM（硬件用户手册）可靠地提取出章节结构和寄存器信息。
2. **值不值得做**：比起"直接把 PDF 丢给 LLM"，MCP 方式在准确性、可追溯性和效率上有没有明显提升。
3. **能不能合规地用**：NDA 资料能否被云端 LLM 读取，以及公司允许用哪些 Agent 工具。

因此，**当前阶段（MCP server 编码之前）的任务是：明确用例、盘点数据、验证解析可行性、设计接口、建立评测基线、确认合规前提。** 这些都完成之后，才进入 prototype 编码。

---

## 2. 阶段定位

| 项目 | 内容 |
|---|---|
| 对应报告中的阶段 | Hardware 第 1 步 "Exploration (Now)"：个人 PC，本地 stdio 进程，SQLite + 文档 + Git |
| 本阶段覆盖的内容类别 | 报告 6 类中的 **① Raw Documents（HW UM）** 和 **③ Structured Data（寄存器）** |
| 暂不涉及 | ② Software（BSP/U-Boot/kernel）、④ Version Mapping、⑤ Know-how/Skills、⑥ Operations（build/flash/EVK）、Remote HTTP 模式、共享服务器、自动更新 pipeline |

### 本阶段目标
- 拿到足够的证据，判断 "HW UM → 寄存器查询 + 章节检索" 这个 prototype 是否值得做、该怎么做。
- 产出 prototype 可以直接照着实现的**数据 schema、工具接口定义、评测问题集**。

### 本阶段非目标
- 不写 MCP server 代码，最多写一些一次性的解析验证脚本（spike），用完可以丢弃。
- 不做多 device 的通用框架，但在设计上保留 `device` 维度（见第 6 节）。
- 不采购硬件，也不搭建共享环境。

---

## 3. 工作项

### W1. 用例收集与标准问题集（最优先）

**为什么**：问题集决定了工具应该怎么设计，同时也是报告中提到的 "Re-test · Standard question set" 的起点。没有它，后面就无法判断做得好不好。

**做什么**：
- 向 FAE、应用工程师、BSP 开发者收集 **30～50 个真实问题**。尽量来自实际的客户咨询或日常工作，不要凭空编造。
- 给每个问题标注：
  - 类型：寄存器精确查询 / 位域含义 / 章节定位 / 跨章节综合 / 超出本阶段范围
  - 标准答案，以及答案的出处（文档号、Rev、页码、章节号）
  - 难度，以及现状下人工查找大约需要多久
- 示例类型（仅示意，实际以收集到的为准）：
  - "某模块某寄存器的地址偏移和复位值是多少？"
  - "某寄存器的 bit[x:y] 是什么含义，可以写哪些值？"
  - "配置某外设时钟需要设置哪些寄存器？出自哪一章？"
  - "某功能的使用限制写在手册哪里？"

**产出**：`question_set_v0.xlsx`（或 YAML），包含问题、类型、标准答案、出处。

---

### W2. RZ/G3L 资料盘点与保密分级

**做什么**：
- 列出 RZ/G3L 相关资料清单：HW UM（是否分卷、页数、当前 Rev）、Datasheet、Errata/Technical Update、App Note、EVK 原理图和 BOM。
- 对每份资料确认：
  - 获取途径（renesas.com 公开 / 内部系统 / NDA）
  - 格式（PDF 是文本型还是扫描型，是否有书签目录）
  - 更新频率，以及历史版本是否还能拿到
- **重点确认：内部有没有机器可读的寄存器源数据。** 例如设计部门的寄存器数据库、IP-XACT、SVD、手册生成前使用的 XML/Excel。如果有，可以直接绕开 PDF 解析，准确性和维护成本都会好得多。**这是本阶段最值得追问的一件事。**

**产出**：资料清单表，包含文档号、Rev、来源、保密级别、格式、是否有结构化源数据。

---

### W3. 数据解析可行性验证（技术 spike）

**为什么**：这是最大的技术风险点。寄存器表一旦提取错误（地址、位域、复位值），比"查不到"的危害更大。

**做什么**（仅在 W2 确认没有结构化源数据时才需要全力做）：
- 选取 HW UM 中 **2～3 个有代表性的章节**，例如一个简单外设、一个复杂外设（寄存器多、表格跨页）、时钟/复位相关章节。
- 用 2～3 种 PDF 解析方案做对比，候选包括 PyMuPDF、pdfplumber、docling、Camelot 等，具体选型在 spike 中决定。验证内容：
  - **章节结构**：书签和标题层级能否还原出章节树，以及"章节号 → 页码范围"的映射
  - **寄存器汇总表**：模块名、寄存器名、地址或偏移、访问宽度、复位值
  - **位域表**：bit 范围、字段名、R/W 属性、复位值、说明；跨页表格和合并单元格的处理
  - **出处**：每条数据能否带上页码
- 把提取结果与人工核对的正确值比较，统计准确率。
- 估算全书规模和人工修正所需工作量。

**判定标准（建议）**：
- 寄存器的关键字段（地址、位域范围、复位值）准确率达到 **≥ 99%**，或者错误能被规则自动检出（例如位域重叠、位宽合计不等于寄存器宽度），然后转人工修正。
- 章节树还原基本完整。

**产出**：spike 报告，内容包括方案对比、准确率、典型失败案例、推荐方案和工作量估算。

### W4. 数据 schema 草案

基于 W3 的结果，定义最小可用的数据模型。示意如下：

```
document   (doc_id, device, title, doc_no, revision, date, source, confidentiality)
section    (section_id, doc_id, number, title, parent_id, page_start, page_end, text)
module     (module_id, device, name, base_address, section_id)
register   (register_id, module_id, name, offset, width, reset_value, access, description, doc_id, page)
field      (field_id, register_id, name, bit_msb, bit_lsb, access, reset_value, description)
```

设计原则：
- **每条数据都必须能追溯到出处**，即产品、文档号、Rev、页码。这一条对应报告中的 "Cite sources"。
- **从第一天起就带上 `device` 和 `revision`**，为多版本和多 device 留好接口。
- 先用 SQLite，同时避免使用 SQLite 特有的写法，方便以后迁移到 PostgreSQL。

**产出**：schema 定义文档，以及用 W3 样本数据填充的示例库。

---

### W5. 工具接口设计（只写文档，不写代码）

**为什么**：报告中强调 "Clear tool description → right tool picked"。工具的名称、描述和参数设计是否合理，决定了 Agent 能不能用对。

**做什么**：
- 对照 W1 的问题集，逐题推演"Agent 会调用哪个工具、传什么参数、得到什么返回"。
- 初始候选（尽量保持少而精，最终以推演结果为准）：

| 工具 | 用途 | 主要参数 |
|---|---|---|
| `search_sections` | 关键词或语义检索手册章节 | `query`, `device`, `top_k` |
| `get_section` | 获取指定章节的正文 | `section_id` 或章节号 |
| `list_modules` | 列出该 device 的外设模块 | `device` |
| `lookup_register` | 按名称或地址精确查找寄存器（含位域） | `device`, `name` / `address` |
| `search_registers` | 模糊查找寄存器或位域 | `device`, `query` |

- 统一规定：返回结果都要带出处；查不到时明确说明"未找到"，不让 Agent 猜测；对返回长度设上限。
- 决定检索方式：先用全文检索（SQLite FTS5）作为基线，再评估是否需要 embedding。报告中提到 embedding 可以走云端或 CPU，需结合 W7 的合规结论决定。

**产出**：工具接口规格书，包括名称、描述文案、参数、返回格式和示例，以及"问题 → 工具调用"的推演表。

---

### W6. 评测基线

**为什么**：如果不先测出"不用 MCP"时的效果，以后就无法证明 MCP 带来了多少价值。

**做什么**：用 W1 的问题集测试以下几种方式，记录正确率、是否给出出处、耗时：
1. LLM 直接回答（不提供资料）
2. LLM 加上 HW UM 的 PDF 附件或上传（如果手册太大放不进上下文，就记录这个限制，它本身也是 MCP 的价值所在）
3. 工程师人工查阅（只抽样记录耗时即可）

之后 prototype 完成时，用同一套问题测试 "LLM + MCP"，进行对比。

**产出**：基线评测结果表，以及评测方法说明（评分规则要写清楚，保证可以重复测试）。

---

### W7. 前提条件与合规确认

这一项需要尽早启动，因为它可能卡住整个项目。

- **AI 工具使用规定**：公司允许使用哪些 Agent 或 LLM（例如 Claude Code、GitHub Copilot、内部部署模型等），以及 NDA 或内部资料是否可以发给云端 LLM。
  - 如果不可以，本阶段只能用公开资料验证，或者需要考虑内部部署模型的方案。
- **资料使用许可**：HW UM 等资料用于构建内部数据库和索引，是否需要申请许可。
- **开发环境**：个人 PC 上能否安装 Python、MCP SDK 等工具，以及代理或网络方面的限制。
- **技术选型初定**：实现语言（建议使用 Python，MCP 官方 SDK 成熟，PDF 解析生态也好）、首选的 Agent host。

**产出**：前提条件确认清单，每项注明结论和确认人。

## 4. 交付物汇总与阶段出口

| # | 交付物 | 对应工作项 |
|---|---|---|
| D1 | 标准问题集 v0（含标准答案和出处） | W1 |
| D2 | RZ/G3L 资料清单（含保密级别、有无结构化源数据） | W2 |
| D3 | PDF 解析 spike 报告 | W3 |
| D4 | 数据 schema 和示例库 | W4 |
| D5 | 工具接口规格书 | W5 |
| D6 | 基线评测结果 | W6 |
| D7 | 前提条件与合规确认清单 | W7 |

**进入 prototype 编码的条件（Go / No-Go）**：
- [ ] W7：确认至少有一种合规可用的 "Agent + 资料" 组合
- [ ] W3：寄存器提取的准确率达标，或者找到了结构化源数据
- [ ] W1/W6：问题集和基线已经建立，并且基线确实暴露出可以改进的地方，例如答错、没有出处、找得慢
- [ ] W5：工具接口通过了问题集的推演，覆盖本阶段范围内的大部分问题

如果条件不满足，就根据卡住的原因调整方向，例如改为只做章节检索、先推动内部提供结构化数据、或者等待合规结论。

## 5. 建议的进行顺序

```
第 1 周   W7 合规确认（尽早发起，可以并行等待结果）
          W2 资料盘点（重点追问有没有结构化源数据）
          W1 问题收集开始
第 2 周   W3 解析 spike
          W1 完成问题集和标准答案
第 3 周   W4 schema、W5 接口设计（基于 W1 问题集推演）
          W6 基线评测
第 4 周   整理所有交付物，开 Go / No-Go 评审
```

以上是按一个人兼职推进估算的，可以根据实际人力调整。W1 需要其他同事配合提供问题，建议第 1 周就发出请求。

## 6. 为扩展到其他 device 做的准备（只做必要的部分）

- schema 和工具参数从一开始就包含 `device`，不要把 RZ/G3L 写死。
- spike 报告中区分哪些解析规则是**手册通用格式**（Renesas HW UM 的共同排版），哪些是 **RZ/G3L 特有的**。这决定了以后扩展到其他 device 的成本。
- 问题集按"通用题型"和"RZ/G3L 具体题"分别组织，通用题型可以复用到其他 device。
- **不要**提前设计多 device 的插件机制或通用框架，等第二个 device 加入时再进行抽象。

## 7. 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| NDA 资料不允许发给云端 LLM | 整体方案受阻 | W7 第一周启动；准备好"只用公开资料"或"内部部署模型"的备选 |
| PDF 寄存器表提取错误 | 给出错误信息，失去用户信任 | 优先寻找结构化源数据；加入规则校验；所有回答都带出处，方便用户核对 |
| 问题集偏离实际需求 | 做出来没人用 | 问题必须来自真实咨询，并请一线 FAE 参与评审 |
| 基线已经足够好（LLM 读 PDF 就能答对） | MCP 的价值不明显 | 这本身就是有用的结论；可以把价值重点转向出处可追溯、多版本管理、Operations 类功能 |
| 手册版本更新导致数据过时 | 回答错误 | 数据带 Rev 信息；本阶段先手动更新，自动 pipeline 放到后续阶段 |

## 8. 需要尽快确认的问题

1. RZ/G3L 的 HW UM，内部有没有生成手册用的寄存器源数据（XML、Excel、IP-XACT 等）？由哪个部门管理？
2. 公司目前允许使用哪些 AI Agent 工具？内部资料（尤其是 NDA 资料）是否可以交给它们处理？
3. 这个 MCP 的首要用户是谁？是 FAE 自己、内部开发者，还是将来面向客户？这会影响资料范围和合规要求。
4. 本阶段有多少人力投入？预计多长时间进行 Go / No-Go 评审？
5. 有没有现成的客户问题记录（工单、FAQ）可以用作问题集的来源？

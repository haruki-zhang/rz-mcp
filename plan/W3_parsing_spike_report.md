# W3 解析可行性验证（Spike）报告 — RZ/G3L HW UM

> 状态：v0.1（2026-11-25）｜对应计划书 W3 / 交付物 D3｜数据：`data/rz.db`，代码：`src/rzmcp/`

## 1. 结论

| 判定项（计划书 W3） | 结果 |
|---|---|
| 章节树还原 | **可以。** HW UM 带 4162 条 PDF 书签，书签页码与 PDF 页码一致；全部 56 份文档中，章节标题在正文中的定位率为 99.8% |
| 寄存器关键字段准确率 ≥99%，或错误能被规则检出 | **3 个试点模块达标。** 详见第 3 节：94% 的寄存器实例经两处独立来源交叉验证一致；解析过程中出现的错误全部被规则检出 |
| 出处 | 每条数据都带文档号、Rev、章节号和页码 |
| 推广到全书 | 规则零修改时，8 个模块完全通过；约 20 个模块需要适配表格变体（不会悄悄出错，都会被规则标出）；其余模块的章节组织方式不同（见第 4 节） |

**建议：** 方案可行，继续采用"PDF 解析 + 规则校验"的路线；同时继续追问内部有没有寄存器源数据（W2），如果有，可以直接替换解析层。

## 2. 方案

- **工具链**：poppler（`pdftotext -layout`、`pdftohtml -xml` 读书签）加 Python 标准库（sqlite3 FTS5）。不依赖 ML 模型，全量重建约 30 秒。
- **A 层（所有文档）**：书签生成章节树，逐页文本去掉页眉页脚，检索单元为"章节在单页内的那一段文字"，建 FTS5 索引。
- **B 层（HW UM 试点模块）**：解析基址表、寄存器总表和每个寄存器的位域表，然后跑校验规则：
  - V0：字段名格式
  - V1：位域覆盖完整且不重叠
  - V2：各字段初始值拼合后等于总表初始值
  - V3：描述页中的地址和宽度与总表一致
  - V4：偏移对齐，且偏移不重复

## 3. 试点结果（WDT / SCIFA / CPG）

| 模块 | 基址 | 寄存器 | 定义 | 位域 | 位域覆盖完整 | 复位值双源一致 | 剩余问题 |
|---|---|---|---|---|---|---|---|
| WDT §5.4 | 9 | 27 | 9 | 13 | 27/27 | 27/27 | 0 |
| SCIFA §7.4 | 18 | 13 | 15 | 66 | 9/9（另有 4 个数据寄存器，手册中没有位域表） | 8/9 | 0（BRR/MDDR 共用偏移，手册注明是有意设计） |
| CPG §4.4 | 3 | 313 | 299 | 2336 | 313/313 | 294/313（19 个含未定义位 x） | 0 |

**冒烟测试**（`eval/smoke_questions.toml`，22 题，答案由独立代理从 PDF 原文核对）：

- 涉及试点模块的 8 道寄存器题：8/8 能从工具输出中完整作答，45 条关键事实中有 44 条直接出现在 `lookup_register` 的输出中。
- 检索命中率：把问题原文直接当查询时，前 8 条结果的命中率为 17/20。这是悲观的下限；未命中的 3 题，换用 Agent 风格的关键词后都能命中。

**解析中遇到并已修复的版式问题**（都是规则先报错，再定位修复）：

- 页首章节号被当作页眉删除
- Word 导出的空标题书签（如 "1."、"1.1"）
- 缩写跨行折断（如 `…_MSTO` 加下一行的 `P`）
- 脚注上标把整行内容挤到下一行（如 `TEIE*1`）
- 位号跨行（`b15 to` / `b11`）
- `R/(W)` 后紧跟描述文字
- 换页后重复出现的两行表头
- 检索时模板名（`GTCCRn`）匹配不到实例名（`GTCCRD`）

## 4. 全书推广试跑（规则零修改）

全书 66 个二级章节，去掉概述类章节后约 45 个外设模块：

- **完全通过（8 个）**：CPG、WDT、SCIFA、VBATTB、USB2.0、ISU2、LVDS、TSU
- **部分通过，需要适配（约 20 个）**：GPT、MTU3a、CAN-FD、I3C、PFC、SYSC、RTC、xSPI、PCIe、RSPI、I2C 等。主要问题有三类：总表或基址表是另一种版式、位域表有变体（多通道合表、表头不同）、字段名被正文污染。
- **未识别到寄存器章节（约 15 个）**：SD、GBETH、RSCI、DMAC、INTC、CRU、LCDC、DSI、DDR、TZC 等。章节结构不同，其中 GBETH 的寄存器只在 NDA 的 Additional Document 中。

**规则的通用性**（对应计划书第 6 节）：目前所有规则都基于 Renesas HW UM 的通用排版，没有 RZ/G3L 专用规则。与器件相关的只有地址空间命名（CA55 / CM33_S / CM33_NS）和试点模块清单（写在 manifest 中）。

**工作量粗估**：每种新的表格变体约需 0.5–1 人日，预计有 5–8 种变体，覆盖大部分模块约需 1–2 周，另外还要人工复核被标记的条目。这只是估算，第二批模块做完后可以给出更准的数字。

## 5. 发现的手册不一致（可作为 MCP 的附加价值）

- **CPG_PLLn_STBY**：描述页写 "Initial Value : Undefined"，总表写 `0000_0000h`（实际值按 n 另见 Table 4.4-5）。
- **CPG_WDTRST_SEL**：CPG 章节给出的初始值是 `0000_0088h`，WDT 章节 p.1210 只列出已定义的位，且全为 0。
- **EVK 启动模式**：模块 EBM p.43 把 boot mode 100 写为 "USB download"，HW UM 中这个编码未分配。

## 6. 局限和下一步

1. 冒烟测试集是代理根据 PDF 起草的，**需要人工抽检**；真实问题集（W1）仍然需要。
2. 端到端效果，也就是 Agent 能不能选对工具，需要通过 MCP 实际试用来评估。调用日志记录在 `data/calls.jsonl`。
3. 下一批模块建议按使用频率选：GPT、RSPI、I2C 和 PFC（引脚复用）。
4. 原理图目前只做了全文检索，网络连接关系没有结构化。

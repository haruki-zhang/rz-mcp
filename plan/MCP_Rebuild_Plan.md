# rz-mcp 改造开发计划（v1.0）

> 2026-11-26。依据当天与用户对齐的结论。适用范围：RZ/G3L。
> 本文取代 `plan/archive/` 下的三份旧文档（PoC 工作流计划、源码证据决定、缺口分析）；它们只作为参考资料保留。

## 0. 摘要

- **目标**：一个 MCP 服务器，提供两类能力：文档查阅（已有，够用）和 PoC 开发全流程（搭环境 → 构想 → 实现和构建 → 自动上板验证 → 交付物）。重点是后者。
- **核心改动**：PoC 流程的每一项能力都做成 **MCP 工具**。不再有需要 agent 知道路径的脚本、需要用户手动输入的斜杠命令、需要装到某个目录的子 Agent。
- **做法**：PoC 部分完全重写，旧代码只当参考。流程从"两轨设计加融合"精简为"单轨设计，一次对齐"。
- **验收**：在任意无关目录下新开的会话里，agent 能选对工具；一个真实 PoC 从头跑到交付，人只做一次设计确认和物理操作（拨码、上下电）。

## 1. 已对齐的结论

| # | 事项 | 结论 |
|---|---|---|
| 1 | 能力的提供形式 | 全部做成 MCP 工具，长任务用"启动 → 查状态"模式 |
| 2 | 构想阶段 | 单轨：agent 写一份设计文档（含上板验证计划），用户确认一次；之后全自动 |
| 3 | BSP 源码工具 | 不做。agent 用自己的文件工具直接读 Yocto 项目里的源码，MCP 只告诉它位置 |
| 4 | 旧代码 | 完全重写。旧代码（git `81df098`）只作为地址、时序、实机日志的参考 |
| 5 | 运行环境 | MCP 服务器、Yocto 构建（Ubuntu 22.04 容器）、EVK 的串口和 USB 网卡、Claude Code 都在同一台 Linux 主机上 |
| 6 | Yocto 范围 | 所有 PoC 共用一个项目，不存在时自动搭建；支持可选组件（graphics、codecs、security、multi-os）。不支持每个 PoC 一个独立项目 |
| 7 | 上板范围 | 串口 + USB 网卡直连（TFTP）；覆盖 eMMC 和 QSPI 的 bootloader 与 rootfs；不用继电器；不做 SD 卡 |
| 8 | 文档查阅 | 现状保留，后续只扩展结构化寄存器的模块覆盖 |
| 9 | 分工 | 主会话（Claude）只做架构、拆解、评审和验收；编码交给按工作包启动的独立会话 |

## 2. 旧实现的问题

对照旧代码得出，对应用户提出的三个问题。

**其他环境下的 agent 不会调用（不稳定）**
- 服务器一共暴露 14 个工具（7 个文档、7 个 BSP）和 1 个 prompt，其中没有任何一个工具能构建、写板或验证。这些能力只存在于 `workflow/` 下的脚本里。
- 流程的唯一入口是 prompt `/rz-docs:poc`。MCP prompt 只能由用户手动输入，模型不能自己调用。
- 两个设计子 Agent 是项目级的，要先用 `install-agents` 复制到 Yocto 项目目录，而且只有在那个目录下打开的会话才能用。
- 服务器名叫 `rz-docs`，服务器说明里只讲文档和 BSP 源码，没有一个字提到构建和上板。
- 结果：在别的目录下，agent 看到的只是一个文档服务器，没有任何线索指向上板工具。

**冗余和过度设计**
- 构想阶段有五步、两个 skill、两个设计 Agent、一个融合 Agent，产出七八个文件。
- 源码快照体系（`snapshot.py`、`src-snapshot`、release/rev 两种视图）加 7 个 BSP 工具，约 1,700 行，只为让 agent 读"未被 PoC 改过的源码"。
- 上板的外围比核心还大：`evk-watch`、`progress.py`、`active.json`、事件流，只为把"需要人操作"转告给用户。
- 每个 PoC 可以有独立的 Yocto 项目，带来项目登记、判定、缓存隔离等一整套状态。
- 流程进度靠"读磁盘上的多处痕迹推断"，规则分散在 prompt 生成代码里。

**功能不清晰**
- 同一件事有三种形态：prompt、脚本、MCP 工具，各管一段。
- 命名看不出用途：`poc-use`、`poc-env`、`build_facts`、`patch_stack`。
- 文档工具和 PoC 工具之间没有统一的说明告诉 agent 什么时候用哪个。

## 3. 设计原则

1. **只有一个表面。** 所有能力都是 MCP 工具。agent 不需要知道 rz-mcp 仓库在哪，不需要特定的工作目录，不需要预装任何东西。
2. **工具做确定的事，agent 做需要判断的事。** 工具负责会改变状态、耗时长、接触硬件的工作。调研、写设计、写代码、写文档由 agent 完成，工具只提供模板和下一步提示。
3. **长任务统一成作业。** 搭环境、构建、写板、验证都立即返回 `job_id`，再用同一个工具查进度和结果。
4. **人的操作是作业的一种状态。** 作业需要人拨码或上电时进入 `waiting_human`，给出一句完整的操作说明。工具从串口判断操作是否完成，不需要人在键盘上应答。
5. **状态显式记录。** 每个工具把结果写进固定的一处，`poc_status` 只读这一处，不再从多处痕迹推断。
6. **工具少，名字直白。** 总数控制在 20 个左右。新增工具必须先说明现有工具为什么做不到。
7. **每一步都能安全重跑。** 中断后重新调用同一个工具，从当前状态接着做。
8. **每个工具都能单独使用。** 流程只存在于 `poc_status` 的“下一步”提示里。任何工具都不检查“上一步是否由流程完成”，只检查自己的输入是否齐全。只有传了 PoC 名称时，工具才把结果记入该 PoC 的状态文件。
9. **先测识别，再写实现。** 工具的名字、描述和服务器说明先定稿并通过识别测试，之后才开始实现（见 6.1）。

## 4. 目标架构

### 4.1 整体

```
任意目录下的 Claude Code 会话
        │  MCP（Streamable HTTP，localhost）
        ▼
rz-mcp 服务器 ── 文档查询层 ── data/rz.db
        │
        ├── 作业管理：每个作业是一个独立子进程，状态在 data/jobs/<id>/
        │       ├── Yocto 作业 ──► 容器里的 bitbake
        │       └── 上板作业 ──► 串口 + USB 网卡（TFTP）──► EVK
        └── config.toml：Yocto 项目目录、容器名、串口、网卡、TFTP 目录、PoC 根目录
```

- 服务器保持无状态 HTTP。作业是脱离服务器的子进程，服务器重启不会中断正在写板的作业。
- 机器相关的值全部放进一个 `config.toml`，代码里不再有写死的 `/home/...` 路径和环境变量。
- 串口独占：同一时间只允许一个上板作业，第二个请求直接返回"正被作业 X 占用"。

### 4.2 工具清单（19 个）

| 组 | 工具 | 作用 | 类型 |
|---|---|---|---|
| 文档（保留） | `list_documents`、`search_docs`、`get_toc`、`get_section`、`read_pages`、`lookup_register`、`search_registers` | 现状不变 | 只读 |
| Yocto | `yocto_status` | 项目是否存在、是否可用、装了哪些可选组件、是否有构建在跑；同时返回源码和产物在磁盘上的位置 | 只读 |
| | `yocto_setup` | 搭建或修复共用项目，按需安装可选组件 | 作业 |
| PoC | `poc_create` | 创建 PoC 仓库骨架：设计模板、验证计划模板、文档模板、层目录 | 即时 |
| | `poc_status` | 列出 PoC；给出某个 PoC 当前处在哪一步、上一步的结果、下一步该调用什么 | 只读 |
| | `poc_build` | 在容器里构建镜像；返回镜像路径或错误摘要。传 PoC 名称时先应用它的层和配置，不传时构建官方镜像 | 作业 |
| | `poc_package` | 生成交付包：层、文档（md 和 pdf）、镜像、README、版本清单、校验和 | 作业 |
| 上板 | `board_status` | 主机检查（串口、网卡、TFTP）和板子当前状态；不写任何东西 | 只读 |
| | `board_flash` | 把任意一个镜像文件（绝对路径）写进 eMMC 或 QSPI（bootloader、rootfs 或两者），写完启动确认。不需要存在 PoC | 作业 |
| | `board_exec` | 在 U-Boot 或 Linux 里执行一条命令并返回输出，用于实验和排查 | 即时 |
| | `board_verify` | 执行一份验证计划（任意文件路径，或用 PoC 名称指代它仓库里的那份），生成验证报告和日志 | 作业 |
| 作业 | `job_status` | 查进度、等待人操作的说明、结果；可带等待时间（长轮询） | 只读 |
| | `job_cancel` | 取消作业 | 即时 |

与旧版相比去掉的东西：prompt、子 Agent、7 个 BSP 工具、`evk-watch`、`poc-use` / `poc-env` / `poc-new` 等脚本、每个 PoC 的独立项目。

### 4.3 作业模型

- 启动类工具立即返回 `job_id`、预计步骤，以及**整个作业需要的全部物理操作清单**，让用户一开始就知道要做几次什么操作。
- `job_status(job_id, wait_seconds)` 返回：状态（`running`、`waiting_human`、`succeeded`、`failed`、`cancelled`）、当前步骤 `i/n`、进度、最近的关键日志行。
- `waiting_human` 时返回一句可以原样转告用户的操作说明。返回文本里明确写"把这句话告诉用户，然后再次调用 job_status"。
- 单次等待上限约 50 秒，避免 HTTP 超时；返回文本里总是写明是否需要继续轮询。
- 失败时返回：失败在哪一步、原因、建议的下一步（例如"重新调用 board_flash 会从 U-Boot 提示符接着做"）。
- 每个作业目录里有 `status.json`、完整日志、`report.md`。

### 4.4 上板验证（重点）

**人工干预的目标值**

| 场景 | 人的操作 |
|---|---|
| 板子能启动到 U-Boot，只换 rootfs | 0 次（最多按一次 RESET） |
| 板子能启动到 U-Boot，换 bootloader | 目标 0 次，取决于调研项 S1 |
| 空板或 bootloader 损坏，做成 eMMC 启动 | 2 次：拨到 SCIF 下载并上电；拨到 eMMC 启动并复位 |
| 空板，做成 QSPI 启动 | 2 次：同上，第二次拨到 QSPI 启动 |
| 执行验证计划 | 0 次；验证项本身要求断电的除外 |

**`board_flash` 的行为要求**
- 写之前自动做完整预检：主机配置、串口、网络、镜像文件齐全且来自同一次构建。预检不过就不碰板子。
- 自动识别板子当前状态（BootROM、Flash Writer、U-Boot、Linux），从当前状态开始，不让人重复操作。
- 每个拨码位置在一次作业里只出现一次；操作顺序按"人的操作次数最少"编排。
- 每次写入后读回校验，最后启动到指定阶段（U-Boot 或 login）作为确认。
- 报告写明：写了什么、写到哪里、sha256、各组件版本、每步耗时。
- 所有写入地址集中在一处，每个值注明文档出处。
- **单独使用时的输入**：只写 rootfs 时，一个 `.wic.gz` 文件就够。写 bootloader 时还需要 BL2、FIP 和 Flash Writer 文件，默认在镜像的同一目录下找，也可以用参数逐个指定；缺文件时在碰板子之前报错并列出缺什么。“bootloader 和 rootfs 来自同一次构建”的检查，在文件由参数逐个指定时降为报告里的一条提示，不阻止写入。

**调研项 S1（实现前先做）**：板子已有可用的 U-Boot 时，能否直接在 U-Boot 里通过 TFTP 更新 eMMC boot 分区和 QSPI 上的 BL2 和 FIP，从而不必切到 SCIF 下载模式。可行则"换 bootloader"也是 0 次人工操作，SCIF 路径只作为空板和救砖的后备。

**`board_verify`**
- 验证计划是一个文件。PoC 流程里它放在 PoC 仓库中，由 agent 在设计阶段写成；单独使用时可以是任意路径的文件，报告写到作业目录。每项在三个位置之一执行：板子的 Linux、主机、启动过程（测各阶段时间）。
- 只按明确的判据判定：期望的输出、返回码、时间上限。
- 结果写成验证报告，逐项对应设计里的验证计划，附原始日志。

**测试手段**
- 写一个假板子（模拟 BootROM、Flash Writer、U-Boot、eMMC、QSPI，提示文字取自实机日志），所有上板代码先对着它测，不需要硬件和 sudo。
- 实机验收见第 6 节。

**主机的一次性配置**：udev 规则、USB 网卡固定 IP、DHCP 和 TFTP 服务需要 sudo，由用户运行一次配置脚本。`board_status` 负责检查并在缺少时给出确切的命令。

### 4.5 PoC 流程

| 步 | 谁做 | 用到的工具 | 产物 |
|---|---|---|---|
| 0 环境 | agent | `yocto_status` → 需要时 `yocto_setup` | 可用的 Yocto 项目 |
| 1 构想 | agent | `poc_create`；文档工具；直接读源码 | `design.md`（方案、改动清单、所需可选组件、风险）和验证计划 |
| 2 对齐 | **用户** | — | 用户确认设计。**全流程唯一的决策关口** |
| 3 实现和构建 | agent | 直接改 PoC 的层；`poc_build`，失败则修改后重试 | 镜像 |
| 4 上板 | agent，人做物理操作 | `board_flash` → `board_verify`；不通过则回到第 3 步 | 验证报告 |
| 5 交付 | agent | 按模板写文档；`poc_package` | 交付包 |

- `poc_status` 在任何时候都能回答"现在在哪一步，下一步调用什么"，新会话靠它接手，不依赖对话历史。
- 每个工具把自己的结果记到 PoC 仓库里固定的一个状态文件（最近一次构建、写入板子的镜像校验和、验证结果）。
- 交付包的样式沿用过去的 PoC：`layers/`、`docs/`（md 和 pdf）、`image/`、README、版本清单、校验和。授权软件包不得进入交付包。

### 4.6 让 agent 选对工具

1. **服务器改名**为 `rz-dev`（暂定）。`rz-docs` 这个名字会让 agent 认为它只管文档。
2. **服务器说明**是每个会话都会加载的内容，按用户意图写："查芯片或板子的资料"、"构建 RZ/G3L 镜像"、"把镜像写进 EVK"、"在板子上验证"分别用哪个工具，中英文关键词都出现。
3. **工具描述的第一句写用户会说的话**（烧录、写板、flash、eMMC、QSPI、Yocto、bitbake、EVK），因为工具数量多时客户端会按关键词检索工具。
4. **工具之间互相指路**：每个返回结果和错误信息都写明下一步该调用哪个工具。
5. **不依赖工作目录**：参数是 PoC 名称或绝对路径，默认值来自服务器配置。
6. **权限**：写板和构建工具会触发 Claude Code 的权限确认。在部署说明里给出一次性的允许配置，否则"高度自动化"会被确认弹窗打断。

## 5. 工作包

主会话负责拆解、评审和验收；每个工作包由一个独立会话实现，按下面的"完成标准"验收。

| P1 | 骨架（**已完成** 2026-11-26）：`config.toml`、作业框架、服务器改名和说明、全部 12 个新工具的接口定稿（先返回"未实现"）、识别测试脚本 | P0 | 识别测试达标（6.1）；作业框架能跑一个假作业，经历 `waiting_human` 并在服务器重启后仍可查询（结果：识别测试 80/80；`eval/test_jobs.py` 5/5） |

**规模约束**：旧版文档以外的代码约 5,000 行（不含测试）。新版同一范围的目标是不超过 3,000 行。超出时先回头检查是否又在过度设计。

### 5.1 P3 / P4 定下的约定（P2 要遵守）

- PoC 仓库 `<poc.root>/<名称>/`：`build.toml`（镜像、可选组件、层、local_conf；`poc_build` 读取，缺的可选组件自动安装）、`design/design.md`（第一行是状态，用户确认后由 agent 改成「状态：已确认 <日期>」）、`design/verify.toml`（`board_verify(plan=<名称>)` 执行它）、`.rz-poc/state.json`（唯一的状态文件）、`.rz-poc/build/`（最近一次成功构建的产物副本，别的构建不会覆盖它）。
- 每次构建的记录写进 `<项目>/.rz-mcp/last-build.json`，`yocto.last_build()` 读取，是 `board_flash` 不带镜像时的默认值。产物键名见 `yocto.BUILD_FILES`：rootfs、bmap、bl2_emmc(_bin)、bl2_qspi(_bin)、fip(_bin)、flash_writer。
- `board_flash` 和 `board_verify` 收到 PoC 名称时，用 `poc.record(名称, "flash" / "verify", ...)` 记录结果，格式见 `src/rzmcp/poc.py` 的模块说明。只写 rootfs 时，要把上一次记录里同一启动设备的 bootloader 校验和带过来。
- 测试用环境变量 `RZ_MCP_CONFIG` 指向另一份配置。

## 6. 验收

面向用户的逐场景验收清单见 [MCP_User_Guide.md](MCP_User_Guide.md)：它同时是使用说明，每个场景写明用户说什么、会发生什么、怎样算通过。本节是三项总体验收的方法和达标线。

### 6.1 识别测试（P1 起，每次改动工具描述后重跑）

- 在一个与本项目无关的空目录下，以无交互方式新开 Claude Code 会话，只连接本服务器。
- 约 12 条用户口吻的请求，中英文混合，例如："把刚构建的镜像烧到 EVK 的 eMMC"、"板子现在能启动吗"、"WDTSET 寄存器的地址是多少"、"给 RZ/G3L 搭一个 Yocto 环境"、"在板子上跑一下验证"。另加几条不该触发任何工具的无关请求。
- 每条重复 5 次，从服务器的调用日志判断第一个被调用的工具是否正确。
- 达标：每条请求至少 4/5 选对；无关请求不触发写板和构建工具。

### 6.2 上板实机验收（P2）

- eMMC：从空板到 `login:`，连续 3 次成功；每次人的操作不超过 2 次。
- QSPI：同上。QSPI 在旧版从未在实机上跑通过，这是首次。
- 只换 rootfs：连续 3 次成功，人的操作 0 次。
- 故障注入：写入中途拔网线、中途取消作业、串口被其他程序占用。每种情况都要给出明确的错误，并且重新调用后能完成。

### 6.3 端到端验收（P5）

- 选一个真实的 PoC 需求，在无关目录下新开会话，只说需求。
- 达标：流程走到交付包；用户只做了一次设计确认和物理操作；中途换一个新会话，靠 `poc_status` 能接着做。
- 记录人工干预的次数和原因，凡是物理操作和设计确认以外的干预都算缺陷。

## 7. 不在范围内

- BSP 源码浏览和源码快照工具
- 两轨设计、融合 Agent、`/in-your-own-words` 和 `/sharpen` 的集成
- 每个 PoC 一个独立的 Yocto 项目
- SD 卡启动、继电器或可控电源
- RZ/G3L 以外的器件
- 基于运行记录的缺口分析工具（旧 `eval/gap/`）
